## เอกสารนี้อ่านอย่างไร

เอกสารนี้บอกว่า **ระบบต้องทำอะไร** ไม่ได้บอกว่าต้องเขียนด้วยภาษา/framework อะไร — คุณเลือกเครื่องมือเองได้ (ดูกรอบที่ล็อกไว้ในข้อ 3) และใช้ AI ช่วยเขียนโค้ดได้เต็มที่ แต่**ต้องอธิบายได้ว่าโค้ดทุกส่วนทำงานอย่างไร**

- อ่านทั้งเล่มหนึ่งรอบก่อนเริ่ม แม้จะยังไม่เข้าใจทุกข้อ — จะได้เห็นว่าแต่ละส่วนเกี่ยวกันตรงไหน
- **จะเริ่มลงมือ ให้ไปที่ข้อ 14.0 (Roadmap) แล้วต่อด้วย 14.5 (งานย่อย 51 งาน มี "วันที่ 1" บอกไว้)** — ทำอะไรก่อนหลัง ทำไม และแต่ละงานเสร็จเมื่อไหร่ · ข้อ 2 บอกว่าต้องขออะไรจากไอทีก่อน
- คำที่ขึ้นต้นด้วย **ต้อง** = บังคับ, **ควร** = ทำถ้าไม่มีเหตุผลที่ดีกว่า, **ไม่ต้อง** = ตั้งใจตัดออกจากรอบนี้ อย่าทำ
- ทุกกฎมี "ทำไม" กำกับ — ถ้าคุณคิดว่ากฎไหนผิด ให้ถาม อย่าแก้เงียบ ๆ
- เจอคำที่ไม่รู้จัก ดูข้อ 1.3 (คำศัพท์) ก่อน
- ถ้าเอกสารกับความเป็นจริงขัดกัน (เช่น API คืนฟิลด์ไม่ตรง) **เอกสารผิด** — แจ้งแล้วเราจะแก้เอกสาร

## 0. สรุปในหนึ่งหน้า

บริษัทใช้ MEMO และใบคำร้องกระดาษ: ผู้จัดทำเขียน → ผู้ตรวจสอบเซ็น → ผู้อนุมัติเซ็น → เก็บแฟ้ม ระบบนี้ย้ายกระบวนการนั้นขึ้นเว็บทั้งหมด

```
ผู้ดูแลฟอร์ม                 พนักงาน                        ผู้อนุมัติ
─────────────               ─────────                      ──────────
ออกแบบฟอร์มบน A4   ──►   เลือกฟอร์ม กรอก แนบไฟล์   ──►   เห็นในกล่องงาน
ตั้งสายอนุมัติ               ส่ง (ได้เลขที่เอกสาร)          อนุมัติ / ไม่อนุมัติ / ส่งกลับแก้ไข
กด "เผยแพร่"                 ดึงกลับได้ถ้ายังไม่มีใครกด        ครบทุกขั้น = อนุมัติครบ → พิมพ์เป็น A4
```

สิ่งที่ทำให้ระบบนี้ต่างจาก Google Forms:

1. **หน้ากรอก = หน้าดู = หน้าพิมพ์ = กระดาษ A4** หน้าตาเหมือนเอกสารจริง ไม่ใช่ฟอร์มเรียงลงมา
2. **สายอนุมัติกำหนดได้ต่อฟอร์ม** กี่ขั้นก็ได้ แต่ละขั้นมีหลายคนได้ ตั้งกฎ "N จาก M" ได้
3. **ทุกอย่างมีหลักฐาน** ใครกดอะไรเมื่อไหร่ ดึงกลับกี่ครั้ง แก้อะไร — เก็บหมด ลบไม่ได้

ระบบใช้ **ภายในบริษัทเท่านั้น** ทุกคน login ผ่าน SSO ของ sellcenter

### 1.3 คำศัพท์

| คำ | ความหมาย |
|---|---|
| **ฟอร์ม (form)** | แม่แบบที่ผู้ดูแลฟอร์มออกแบบ เช่น "MEMO ขออนุมัติ", "ใบขอซื้อ" มีสถานะ ร่าง/เผยแพร่/ปิดรับ |
| **คำร้อง (submission)** | ฟอร์มที่พนักงานกรอกแล้ว 1 ใบ มีเลขที่เอกสาร มีสถานะ ร่าง/รอดำเนินการ/อนุมัติครบ/ไม่อนุมัติ/ยกเลิก |
| **ผู้ยื่น (submitter)** | พนักงานที่สร้างคำร้อง |
| **สายอนุมัติ (workflow)** | ลำดับของ **ขั้น (step)** ที่คำร้องต้องผ่าน ตั้งไว้ในฟอร์ม |
| **ขั้น (step)** | จุดหยุดหนึ่งจุดในสาย มีชื่อ (เช่น "ผู้ตรวจสอบ") มีผู้อนุมัติ 1 คนขึ้นไป มีกฎ N จาก M |
| **ผู้อนุมัติ (approver)** | คนที่มีสิทธิ์กดในขั้นนั้น |
| **N จาก M** | ขั้นมีผู้อนุมัติ M คน ต้องได้ "อนุมัติ" N คนถึงจะผ่านขั้น |
| **รอบ (round)** | ช่วงตั้งแต่ "ส่ง" จนถึง "จบสาย" หรือ "ถูกดึงกลับ/ส่งกลับแก้ไข" — ส่งใหม่ = รอบใหม่ |
| **ดึงกลับ (recall)** | คนที่กระทำล่าสุดถอนการกระทำของตัวเอง ทำได้เฉพาะตอนที่คนถัดไปยังไม่กด |
| **ส่งกลับแก้ไข (return)** | ผู้อนุมัติส่งคำร้องคืนผู้ยื่นให้แก้ โดยยังไม่ตัดสินว่าไม่อนุมัติ |
| **snapshot** | สำเนาโครงฟอร์ม + สายอนุมัติที่คัดลอกฝังลงในคำร้อง ณ ตอนส่ง เพื่อให้คำร้องไม่เปลี่ยนแม้ฟอร์มถูกแก้ทีหลัง |
| **เลขที่เอกสาร** | รหัสไม่ซ้ำของคำร้อง เช่น `MEMO-2569-0042` |
| **หัวกระดาษ (letterhead)** | ส่วนบนสุดของ A4: โลโก้ + ชื่อบริษัท admin ตั้งไว้ ผู้ดูแลฟอร์มเลือกต่อฟอร์ม |
| **SSO** | การ login ผ่านระบบกลางของบริษัท (sellcenter `/system81`) ผู้ใช้ไม่มีรหัสผ่านในระบบนี้ |
| **API ผังองค์กร** | API ของ sellcenter ที่บอกว่าใครอยู่แผนกไหน ใครเป็นหัวหน้าใคร (ข้อ 6) |

## 3. กรอบเทคนิคที่ล็อกไว้

เลือก framework/ภาษา/UI library ได้อิสระ **แต่ 6 ข้อนี้ห้ามเปลี่ยน**:

### 3.1 รันด้วย `docker compose up` คำสั่งเดียว

- ส่งมอบ `Dockerfile` + `docker-compose.yml` ที่ `git clone` → `cp .env.example .env` → `docker compose up` แล้วใช้งานได้ที่ `http://localhost:<port>`
- compose สำหรับ dev ต้องมี **MongoDB 5 แบบ standalone** (ไม่ใช่ replica set — ให้เหมือน production) และ volume สำหรับไฟล์แนบ — **ใช้ไฟล์ในภาคผนวก E.2 ตรง ๆ** อย่าตั้งเอง
- compose สำหรับ production ไม่มี Mongo (ต่อ `digital.in.th` ผ่าน `MONGODB_URI`)
- **คุณไม่ deploy เอง** — ไอที `git pull` จาก branch `main` แล้ว `docker compose -f docker-compose.prod.yml up -d --build` บน server ตาม README ของคุณ ดังนั้น README ส่วน deploy ต้องทำตามได้โดยไม่ต้องถามคุณ
- **ทำไม**: ฝ่ายไอทีต้อง deploy และแก้ต่อได้หลังคุณหมดสัญญา โดยไม่ต้องรู้ว่าคุณใช้เครื่องมืออะไร

### 3.2 MongoDB v5 แบบ standalone — ไม่มี transaction

Production คือ MongoDB 5 บน `digital.in.th` ที่**ไม่ได้รันเป็น replica set** ผลคือ:

| ใช้ไม่ได้ | ทำแทนด้วย |
|---|---|
| multi-document transaction (`session.startTransaction`) | ออกแบบให้ทุกการเปลี่ยนสถานะเป็น **update เอกสารเดียว** (ข้อ 11.1) |
| change streams | polling (กล่องงาน refresh ทุก 30 วินาที) |
| **Prisma** (บังคับ replica set แม้ไม่ใช้ transaction) | driver ทางการ (`mongodb` npm), Mongoose, PyMongo, หรือเทียบเท่าในภาษาที่เลือก |

กฎ 4 ข้อที่ต้องทำตาม (รายละเอียดข้อ 11):
1. **คำร้อง 1 ใบ = เอกสารเดียว** ฝังทุกอย่าง (ค่าที่กรอก, snapshot, ประวัติการอนุมัติ, ไฟล์แนบ)
2. **ทุกปุ่มใช้ `findOneAndUpdate` แบบมีเงื่อนไข + ฟิลด์ `version`** ป้องกันคนกดพร้อมกัน
3. **เลขที่เอกสารใช้ `$inc` บน collection `counters`** ไม่อ่านแล้วบวกเอง
4. **ไฟล์เขียนลง disk ก่อน แล้วค่อยบันทึกลงเอกสาร** ไฟล์กำพร้ามี job กวาดวันละครั้ง

- **ทำไม**: ถ้าเขียนโค้ดที่พึ่ง transaction จะรันได้ที่บ้าน (ถ้าเผลอตั้ง replica set) แต่พังตอน deploy — เป็น bug ประเภทที่หาเจอยากที่สุด
- ถ้า AI แนะนำ Prisma หรือ transaction — **ปฏิเสธ** และบอกมันว่า "MongoDB standalone, no transactions"

### 3.3 โค้ดอยู่บน GitHub บริษัทตั้งแต่วันแรก

- `git push` ทุกวันที่ทำงาน (ข้อ 17)
- ห้ามมีโค้ดที่อยู่แค่ในเครื่องคุณเกิน 1 วันทำงาน

### 3.4 ค่าตั้งค่าทั้งหมดผ่าน `.env`

- มี `.env.example` ที่ครบทุกตัวแปรพร้อมคำอธิบาย, `.env` จริงอยู่ใน `.gitignore`
- ห้ามมี URL, รหัสผ่าน, token, secret ในโค้ดแม้แต่ค่า default
- ระบบต้อง **fail ตอน start** พร้อมข้อความชัดเจนถ้าตัวแปรจำเป็นหาย ไม่ใช่พังทีหลังตอนมีคนกดปุ่ม

ตัวแปรขั้นต่ำ:

```
APP_URL=http://localhost:3000          # URL ที่ผู้ใช้เปิด ใช้สร้างลิงก์ในอีเมล + redirect_uri
PORT=3000
MONGODB_URI=mongodb://mongo:27017/its_forms
SESSION_SECRET=                         # สุ่มยาว ≥ 32 ตัวอักษร
SELLCENTER_URL=https://digital.in.th    # SSO + org API
ORG_API_TOKEN=                          # service token scope org:read
AUTH_MODE=sso                           # sso | mock  (mock ใช้ได้เฉพาะ dev — ข้อ 5.6)
ADMIN_EMP_IDS=                          # รหัสพนักงานที่เป็น admin ตั้งแต่แรก คั่นด้วย ,
UPLOAD_DIR=/data/uploads
MAX_FILE_MB=10
SMTP_HOST= SMTP_PORT= SMTP_USER= SMTP_PASS= SMTP_FROM=
MAIL_MODE=smtp                          # smtp | console (console = พิมพ์ลง log ไม่ส่งจริง)
TZ=Asia/Bangkok
```

### 3.5 ไม่ใช้บริการเสียเงินเพิ่ม

- ไม่ใช้ cloud DB, S3, Firebase, SaaS ส่งอีเมล, CDN เสียเงิน โดยไม่ขออนุมัติก่อน
- ไฟล์แนบเก็บบน disk ของ server (volume) เท่านั้น
- library open-source ใช้ได้ตามปกติ

- ตัวเลขเงินแสดง `1,234.50` และรับกรอกได้ทั้งมีและไม่มี comma
- ฟอนต์บนหน้า A4 ต้องเป็นฟอนต์ไทยที่พิมพ์แล้วสวย (แนะนำ **Sarabun** จาก Google Fonts หรือฝังไฟล์ฟอนต์ไว้ในโปรเจค) — ห้ามปล่อยเป็นฟอนต์ default ของ browser

## 4. ผู้ใช้และบทบาท

ทุกคนที่ login ผ่าน SSO ได้ = **พนักงาน** โดยอัตโนมัติ บทบาทอีก 2 แบบ admin ตั้งให้

| สิทธิ์ | พนักงาน | ผู้ดูแลฟอร์ม | Admin |

| ดู audit log | | | ✔ |

กฎสำคัญ:
- **คำร้องเป็นความลับระดับ "คนที่เกี่ยวข้อง"** — พนักงาน A เปิดคำร้องของ B ไม่ได้ ถ้า A ไม่ได้อยู่ในสายอนุมัติของใบนั้น ระบบต้องตอบ 403 ไม่ใช่แค่ซ่อนลิงก์
- Admin คนแรกมาจาก `ADMIN_EMP_IDS` ใน `.env` หลังจากนั้นตั้งเพิ่มในหน้าตั้งค่าได้
- ผู้ดูแลฟอร์มเป็นสิทธิ์**ระดับระบบ** (admin ตั้ง) ส่วน "ผู้ดูแลร่วม" เป็น**ระดับฟอร์ม** (เจ้าของฟอร์มตั้ง) — คนที่เป็นผู้ดูแลร่วมได้ต้องเป็นผู้ดูแลฟอร์มอยู่แล้ว
- พนักงานที่ `is_active=false` ใน API ผังองค์กร: login ไม่ได้ แต่ชื่อยังแสดงในคำร้องเก่าได้

## 5. การเข้าสู่ระบบ — คู่มือเชื่อม SSO

ระบบนี้**ไม่มีรหัสผ่านของตัวเอง** ผู้ใช้ login ที่หน้า login กลางของ sellcenter (`/system81/login`) แล้วถูกส่งกลับมาพร้อม token คุณไม่ต้องเข้าใจ OAuth — ทำตาม 5 ขั้นนี้ตรง ๆ

### 5.1 ภาพรวม

```mermaid
sequenceDiagram
    participant B as Browser
    participant F as its-forms
    participant S as sellcenter

    B->>F: GET /auth/login
    F->>F: สุ่ม state เก็บใน cookie (5 นาที)
    F-->>B: redirect ไป sellcenter
    B->>S: GET /system81/login?redirect_uri=<APP_URL>/auth/callback?state=xxx&app_name=its-forms
    S-->>B: หน้า login (username/password ของ itime)
    B->>S: POST username/password
    S-->>B: redirect กลับ <APP_URL>/auth/callback?state=xxx&token=<jwt>
    B->>F: GET /auth/callback?state=xxx&token=<jwt>
    F->>F: เทียบ state กับ cookie — ไม่ตรง = ปฏิเสธ
    F->>S: GET /system81/userinfo (Authorization: Bearer <jwt>)
    S-->>F: { success, user: { sub, username, name, emp_id, department, position } }
    F->>S: GET /api/org/employees/<emp_id> (x-service-token)
    S-->>F: ข้อมูลพนักงานเต็ม (แผนก ตำแหน่ง หัวหน้า)
    F->>F: upsert users, สร้าง session ของตัวเอง
    F-->>B: set-cookie session; redirect ไป /inbox
```

### 5.2 ขั้นที่ 1 — เริ่ม login (`GET /auth/login`)

1. สุ่ม `state` (ค่าสุ่ม 16 byte เข้ารหัส base64url)
2. เก็บ `state` ใน cookie ชื่อ `sso_state` (httpOnly, อายุ 5 นาที)
3. สร้าง `redirect_uri` = `{APP_URL}/auth/callback?state={state}`
4. redirect ผู้ใช้ไปที่:

```
{SELLCENTER_URL}/system81/login?redirect_uri={redirect_uri ที่ URL-encode แล้ว}&app_name=its-forms
```

ของจริง (dev ที่บ้าน `APP_URL=http://localhost:3000`):
```
https://digital.in.th/system81/login?redirect_uri=http%3A%2F%2Flocalhost%3A3000%2Fauth%2Fcallback%3Fstate%3DabC123&app_name=its-forms
```
`localhost` ใช้ได้เพราะ redirect เกิดใน browser ของคุณ ไม่ใช่จาก server ของ sellcenter

- `app_name` แสดงบนหน้า login ให้ผู้ใช้รู้ว่ากำลัง login เข้าระบบอะไร
- ไม่ต้องลงทะเบียน client, ไม่มี client_id/secret — sellcenter รับ `redirect_uri` อะไรก็ได้
- **ทำไมต้องมี state**: ป้องกันคนส่งลิงก์ callback ปลอมมาให้เหยื่อคลิก (CSRF) — sellcenter ไม่มี state ของตัวเอง เราจึงฝังไว้ใน redirect_uri แล้วมันจะกลับมาครบ

### 5.3 ขั้นที่ 2 — รับ callback (`GET /auth/callback?state=…&token=…`)

sellcenter จะ redirect กลับมาพร้อม **ต่อท้าย** `token=<jwt>` ให้ (ถ้า redirect_uri มี `?` อยู่แล้วจะต่อด้วย `&`)

1. อ่าน `state` จาก query และจาก cookie `sso_state` → ต้องตรงกันและ cookie ต้องยังไม่หมดอายุ ไม่งั้นแสดง "เซสชัน SSO หมดอายุ กรุณาลองใหม่" แล้วจบ
2. ลบ cookie `sso_state` ทันที (ใช้ได้ครั้งเดียว)
3. ถ้าไม่มี `token` → แสดง error แล้วจบ

### 5.4 ขั้นที่ 3 — ตรวจ token กับ sellcenter

**ห้าม decode/verify JWT เอง** — คุณไม่มี secret และไม่ควรมี ให้ sellcenter ตรวจให้:

```
GET {SELLCENTER_URL}/system81/userinfo
Authorization: Bearer <token>
```

ตอบกลับ (สำเร็จ):
```json
{
  "success": true,
  "user": {
    "iss": "system81",
    "sub": "64b000000000000000000002",
    "username": "dev@company.com",
    "name": "สมชาย ใจดี",
    "emp_id": "E002",
    "department": "64a000000000000000000001",
    "position": "it_dev"
  }
}
```

ตอบกลับ (token ผิด/หมดอายุ): HTTP 401 `{"success": false, "msg": "invalid_or_expired_token"}` → แสดง "เข้าสู่ระบบไม่สำเร็จ ลองใหม่" แล้วส่งกลับไปขั้นที่ 1

ข้อควรรู้:
- **ไม่มีฟิลด์ `email`** — `username` ของ itime คืออีเมลอยู่แล้ว ใช้ `username` เป็นอีเมล (แปลงเป็นตัวพิมพ์เล็ก)
- **`department` และ `position` เป็น id ไม่ใช่ชื่อ** — ชื่อจริงเอาจาก API ผังองค์กร (ขั้นถัดไป)
- `sub` = `_id` ของผู้ใช้ใน itime ตรงกับ `id` ใน API ผังองค์กร
- token ของ sellcenter อายุ 9 ชั่วโมง ไม่มี refresh — **ไม่ต้องเก็บ token ไว้** ใช้ครั้งเดียวตอน login แล้วทิ้ง

### 5.5 ขั้นที่ 4 — เติมข้อมูลจาก API ผังองค์กร แล้วสร้าง session ของเราเอง

1. เรียก `GET {SELLCENTER_URL}/api/org/employees/{emp_id}` ด้วย header `x-service-token: {ORG_API_TOKEN}` (รายละเอียดข้อ 6)
2. ถ้า `is_active` เป็น `false` → ปฏิเสธ login "บัญชีนี้ไม่ได้ใช้งานแล้ว"
3. upsert ลง collection `users` ของเรา (คีย์ = `emp_id`) เก็บ: `emp_id, sub, email, name, nickname, department{id,name}, position{id,name}, chief{emp_id,name}, is_active, lastLoginAt` — บทบาท (`roles`) ของเราเก็บในเอกสารเดียวกันแต่**ห้ามถูก overwrite** ตอน upsert
4. ถ้า API ผังองค์กรล่ม → ใช้ข้อมูลใน `users` ที่มีอยู่ (ถ้าเคย login) หรือข้อมูลจาก userinfo (ชื่อแผนกจะว่าง) — **SSO ล่มไม่ได้แปลว่าระบบใช้ไม่ได้**
5. สร้าง **session ของระบบเราเอง** (cookie httpOnly, secure เมื่อเป็น https, SameSite=Lax, อายุ 9 ชั่วโมงหรือน้อยกว่า) เก็บแค่ `emp_id` + เวลาหมดอายุ — ใช้ library session ของ framework ที่เลือก
6. redirect ไป `/inbox`

**Logout** (`POST /auth/logout`): ลบ session ของเรา แล้ว redirect ไป `{SELLCENTER_URL}/system81/logout?redirect_uri={APP_URL}` เพื่อให้ sellcenter ล้าง cookie ของมันด้วย

### 5.6 โหมด mock สำหรับพัฒนาที่บ้าน (`AUTH_MODE=mock`)

ตอนยังไม่ได้ URL/บัญชีทดสอบ หรือ sellcenter เข้าไม่ได้ ต้องมีทาง login โดยไม่พึ่ง sellcenter:

- หน้า `/auth/login` แสดง dropdown เลือกพนักงานจาก mock JSON (ภาคผนวก A) กดแล้ว login เป็นคนนั้นทันที
- ทำงานเฉพาะเมื่อ `AUTH_MODE=mock` — ถ้า `AUTH_MODE=sso` route นี้ต้องไม่มีอยู่เลย (404) ไม่ใช่แค่ซ่อนปุ่ม
- ตอน start ถ้า `AUTH_MODE=mock` ต้อง log เตือนตัวใหญ่ ๆ ว่า "MOCK AUTH ENABLED — DO NOT USE IN PRODUCTION"
- **ทำไม**: เพื่อให้คุณทำงานต่อได้โดยไม่ต้องรอไอที และเพื่อให้ทดสอบ "login เป็น 4 คนสลับกันกด" ได้เร็ว

### 5.7 ตัวอย่างโค้ด (JavaScript — ให้ AI แปลงเป็นภาษาที่เลือก)

```js
// GET /auth/login
async function login(req, res) {
  const state = crypto.randomBytes(16).toString('base64url');
  res.cookie('sso_state', state, { httpOnly: true, maxAge: 5 * 60 * 1000, sameSite: 'lax' });
  const redirectUri = `${process.env.APP_URL}/auth/callback?state=${state}`;
  const url = new URL('/system81/login', process.env.SELLCENTER_URL);
  url.searchParams.set('redirect_uri', redirectUri);
  url.searchParams.set('app_name', 'its-forms');
  res.redirect(url.toString());
}

// GET /auth/callback
async function callback(req, res) {
  const { state, token } = req.query;
  if (!state || !token || state !== req.cookies.sso_state) {
    return res.redirect('/auth/error?code=STATE_MISMATCH');
  }
  res.clearCookie('sso_state');

  const r = await fetch(new URL('/system81/userinfo', process.env.SELLCENTER_URL), {
    headers: { Authorization: `Bearer ${token}` },
  });
  if (!r.ok) return res.redirect('/auth/error?code=SSO_FAILED');
  const body = await r.json();
  if (!body.success || !body.user || !body.user.emp_id) return res.redirect('/auth/error?code=SSO_FAILED');

  const emp = await orgApi.getEmployee(body.user.emp_id);          // ข้อ 6 — อาจคืน null ถ้า API ล่ม
  if (emp && emp.is_active === false) return res.redirect('/auth/error?code=INACTIVE');

  await users.upsertFromSso(body.user, emp);                        // ห้าม overwrite roles
  req.session.emp_id = body.user.emp_id;
  res.redirect('/inbox');
}
```

### 5.8 เช็คลิสต์ว่า SSO ถูกต้อง

- [ ] เปิด `/auth/login` แล้วไปโผล่หน้า login ของ sellcenter ที่มีชื่อ "its-forms"
- [ ] login สำเร็จ กลับมาที่ `/inbox` เห็นชื่อ + แผนกของตัวเองถูกต้อง (ชื่อแผนกเป็นภาษาไทย ไม่ใช่ id)
- [ ] เปิด `/auth/callback?state=ปลอม&token=อะไรก็ได้` → ถูกปฏิเสธ
- [ ] กด callback เดิมซ้ำ (refresh) → ถูกปฏิเสธ (state ใช้ได้ครั้งเดียว)
- [ ] ปิด sellcenter (ตั้ง `SELLCENTER_URL` ผิด) → login ใหม่ไม่ได้ แต่คนที่ login ค้างอยู่ยังใช้งานได้จนหมด session
- [ ] ทุก route ยกเว้น `/auth/*` และไฟล์ static → ไม่มี session = redirect ไป `/auth/login`
- [ ] logout แล้วกด back → เข้าหน้าเดิมไม่ได้

## 6. API ผังองค์กร (sellcenter Org Directory API)

สเปกฉบับเต็ม (ทุก endpoint, ทุกฟิลด์, error ทุกแบบ) อยู่ใน **ภาคผนวก D** — สรุปที่ต้องใช้:

| Endpoint | ใช้ทำอะไร |
|---|---|
| `GET /api/org/employees` | รายชื่อพนักงาน active ทั้งหมด — ใช้ตอน "เลือกผู้อนุมัติ", "เลือกผู้ดูแลร่วม", sync `users` |
| `GET /api/org/employees?department=<id>` | พนักงานในแผนก — ใช้เมื่อสายอนุมัติจำกัดแผนก |
| `GET /api/org/employees/:emp_id` | รายคน (ไม่กรอง active) — ใช้ตอน login และตอน resolve ผู้อนุมัติ |
| `GET /api/org/departments` | แผนกทั้งหมด + `head` (หัวหน้าแผนก) — ใช้ resolve "ผู้จัดการฝ่ายของผู้ยื่น" |

Header ทุก request: `x-service-token: {ORG_API_TOKEN}` · 401 = ไม่ได้ส่ง token · 403 = token ผิด/ไม่มี scope

โครง employee:
```json
{
  "id": "64b000000000000000000002",
  "emp_id": "E002",
  "email": "dev@company.com",
  "name": "สมชาย ใจดี",
  "first_name": "สมชาย", "last_name": "ใจดี", "nickname": "ชาย",
  "picture": null,
  "department": { "id": "64a000000000000000000001", "name": "ฝ่ายไอที" },
  "position":   { "id": "it_dev", "name": "โปรแกรมเมอร์" },
  "chief":      { "emp_id": "E001", "name": "นิมิต คงอำนาจ" },
  "is_active": true
}
```

กฎการใช้:
- **cache ฝั่งเรา 10 นาที** (in-memory หรือใน collection `users` พร้อม `syncedAt`) — ห้ามยิง API ทุกครั้งที่เปิดหน้า
- **sync `users` วันละครั้ง** (job) ดึง `/api/org/employees?active=all` → upsert ทุกคน เพื่อให้ชื่อคนที่ลาออกยังแสดงในคำร้องเก่า และเพื่อให้ dropdown เลือกคนไม่ต้องรอ API
- API ล่ม → ใช้ `users` ที่ cache ไว้ + แสดงแถบเตือนเล็ก ๆ ว่า "ข้อมูลพนักงานอาจไม่เป็นปัจจุบัน" — **ห้ามทำให้ยื่น/อนุมัติไม่ได้**
- ระหว่างยังไม่มี token ใช้ mock: ตั้ง `ORG_API_MOCK=1` ให้ client ของคุณอ่านจากไฟล์ JSON ในภาคผนวก A แทน — โครง JSON ต้องเหมือนของจริง 100% เพื่อให้สลับเป็นของจริงได้โดยไม่แก้โค้ดอื่น

การ resolve ผู้อนุมัติแบบ "ตำแหน่งสัมพัทธ์" (ใช้ในข้อ 7.5):

| กฎในสายอนุมัติ | ค่าที่ใช้ | ถ้าไม่มี |
|---|---|---|
| หัวหน้าโดยตรงของผู้ยื่น | `employee.chief.emp_id` | บล็อกการส่ง แจ้ง "ไม่พบหัวหน้าโดยตรงของคุณในระบบ ติดต่อฝ่ายไอที" |
| ผู้จัดการฝ่ายของผู้ยื่น | `departments[employee.department.id].head.emp_id` | บล็อกการส่ง แจ้งเช่นเดียวกัน |
| ทุกคนในแผนก X | `/api/org/employees?department=X` | บล็อกถ้าได้ 0 คน |

## 7. ฟอร์ม

### 7.1 วงจรสถานะฟอร์ม

```
ร่าง (draft) ──เผยแพร่──▶ เผยแพร่ (published) ──ปิดรับ──▶ ปิดรับ (closed)
   ▲                          │                              │
   └────── แก้ไขได้เสมอ ───────┘                              └─ เปิดรับใหม่ได้
```

| สถานะ | พนักงานยื่นได้ | แก้โครงได้ | หมายเหตุ |
|---|:---:|:---:|---|
| ร่าง | ✘ | ✔ | ยังไม่มีใครเห็น |
| เผยแพร่ | ✔ | ✔ (ดู 7.8) | ปรากฏในหน้า "เลือกฟอร์ม" |
| ปิดรับ | ✘ | ✔ | คำร้องที่ค้างอยู่**เดินต่อจนจบ** ยื่นใหม่ไม่ได้ |

- ลบฟอร์มได้เฉพาะเมื่อ**ไม่เคยมีคำร้อง**เลย ถ้ามีแล้วให้ "ปิดรับ" แทน (**ทำไม**: คำร้องเก่าอ้างถึงฟอร์ม ลบแล้วรายงานพัง)
- "คัดลอกฟอร์ม" สร้างฟอร์มใหม่สถานะร่าง โครงเหมือนเดิม ชื่อต่อท้าย "(สำเนา)"

### 7.2 ตัวออกแบบกระดาษ A4 (ลาก-วาง)

**แนวคิด**: ผู้ดูแลฟอร์มเห็นกระดาษ A4 แนวตั้งบนจอ ลากองค์ประกอบมาวางบนกริด เหมือนจัดหน้าเอกสารใน Word แต่ผลลัพธ์เป็นเว็บที่กรอกได้

**กริด**
- กระดาษ A4 แนวตั้ง 210 × 297 มม. ขอบกระดาษ 15 มม. ทุกด้าน → พื้นที่เนื้อหา 180 มม.
- แบ่งแนวนอนเป็น **24 คอลัมน์** เท่ากัน (คอลัมน์ละ 7.5 มม.) ระยะห่างระหว่างองค์ประกอบ 2 มม.
- แนวตั้งเป็น **แถว** เลขที่ 1, 2, 3, … **ความสูงของแถวไม่คงที่** — ยืดตามเนื้อหาที่สูงที่สุดในแถวนั้น
- เส้นกริดเปิด/ปิดได้ในโหมดออกแบบ, ไม่แสดงตอนกรอก/ดู/พิมพ์

**องค์ประกอบ (element)** ทุกชิ้นมี:

| property | ความหมาย |
|---|---|
| `id` | ไม่ซ้ำภายในฟอร์ม สุ่มตอนสร้าง **ไม่เปลี่ยนเมื่อย้ายตำแหน่ง** (ค่าที่กรอกอ้างอิงด้วย id นี้) |
| `type` | หนึ่งใน 10 ชนิด (7.3) |
| `row` | แถวที่วาง (≥ 1) |
| `col` | คอลัมน์เริ่ม (1–24) |
| `colSpan` | กว้างกี่คอลัมน์ (1–24, `col + colSpan − 1 ≤ 24`) |
| `align` | `left` / `center` / `right` — จัดเนื้อหาภายในกล่อง |
| `props` | ค่าเฉพาะชนิด (label, required, options, …) |

**กฎการวาง**
- สององค์ประกอบในแถวเดียวกัน**ห้ามซ้อนคอลัมน์กัน** — ระบบต้องปฏิเสธการวาง (เด้งกลับ + ไฮไลต์แดง) ไม่ใช่ปล่อยให้ทับ
- ลากไปวางแถวว่างระหว่างกลาง = แทรกแถวใหม่ ดันแถวถัดไปลง
- ลบองค์ประกอบสุดท้ายในแถว = แถวหายไป (ไม่เหลือแถวว่างค้าง)
- ปุ่ม **Tab** ในโหมดออกแบบ: ย้าย selection ไปองค์ประกอบถัดไป (ซ้าย→ขวา, บน→ล่าง), **Shift+Tab** ย้อนกลับ, ลูกศร = ขยับทีละคอลัมน์/แถว, Delete = ลบ
- ทุกการเปลี่ยนแปลงมี **Undo/Redo** (Ctrl+Z / Ctrl+Y) อย่างน้อย 50 ขั้น
- บันทึกอัตโนมัติทุก 10 วินาทีเมื่อมีการเปลี่ยน + ปุ่มบันทึกเอง แสดงสถานะ "บันทึกแล้ว 14:32:05"
- ตัวออกแบบเป็น **desktop เท่านั้น** (≥ 1024px) บนมือถือแสดงข้อความ "กรุณาออกแบบฟอร์มบนคอมพิวเตอร์"

**ส่วนหัวและท้ายกระดาษ (ไม่ใช่องค์ประกอบ ผู้ออกแบบย้ายไม่ได้)**
- หัวกระดาษ: เลือกจากรายการที่ admin ตั้ง (โลโก้ + ชื่อบริษัท + ที่อยู่) หรือ "ไม่มี"
- ใต้หัวกระดาษ: ชื่อฟอร์ม (ตั้งใน 7.6) + เลขที่เอกสาร (ขวาบน) — ตำแหน่งตายตัว
- ท้ายกระดาษ: **ตารางการอนุมัติ** สร้างอัตโนมัติจากสายอนุมัติ (ข้อ 8.7)

**การแบ่งหน้า**
- เนื้อหายาวเกิน 1 หน้า A4 → ขึ้นหน้า 2 อัตโนมัติ **ตัดที่ขอบแถว** ไม่ตัดกลางแถว (`break-inside: avoid` ต่อแถว)
- ตารางรายการที่ยาวมากอาจถูกตัดกลางตารางได้ แต่ต้องซ้ำหัวตารางบนหน้าใหม่ (`thead` + `display: table-header-group`)
- ตารางการอนุมัติต้องอยู่หน้าเดียวกันทั้งตาราง (ไม่แยกครึ่ง)
- หัวกระดาษแสดงเฉพาะหน้าแรก, เลขหน้า "หน้า 1/2" มุมล่างขวาทุกหน้า

**เหตุผลที่ไม่ใช่ลาก-วางแบบพิกัดอิสระ (x, y)**: ตอนกรอกจริง ข้อความยาว/ตารางเพิ่มแถว/ไฟล์แนบ 10 ไฟล์ จะทำให้กล่องล้นทับกล่องข้างล่าง กริดแบบแถวยืดตามเนื้อหาให้ความรู้สึกตอนออกแบบเหมือนกัน แต่ไม่ทับกันตอนใช้จริง — ใช้ CSS Grid ธรรมดา `grid-column: {col} / span {colSpan}` พิมพ์ออกมาถูกต้องเอง

### 7.3 ชนิดฟิลด์ (10 ชนิด — ทั้งหมดอยู่ใน v1)

ทุกชนิดที่รับข้อมูลมี `label` (ข้อความกำกับ), `required` (บังคับกรอก), `helpText` (คำอธิบายเล็ก ๆ ใต้ช่อง ไม่พิมพ์ออกกระดาษ)

| # | `type` | ใช้กับ | props เพิ่มเติม | ค่าที่เก็บ | validation |
|---|---|---|---|---|---|
| 1 | `short_text` | เรื่อง, ชื่อ | `maxLength` (default 200), `placeholder` | string | ความยาว |
| 2 | `long_text` | รายละเอียด, เหตุผล | `maxLength` (default 5000), `rows` (สูงเริ่มต้น) | string (เก็บ line break) | ความยาว |
| 3 | `number` | จำนวนเงิน, จำนวน | `min`, `max`, `decimals` (0–4), `prefix` ("฿"), `suffix` ("บาท") | number | ช่วง, ทศนิยม |
| 4 | `date` | วันที่, ช่วงวันที่ | `mode`: `single` / `range`, `minDate`, `maxDate` (หรือ `today`) | `{from, to?}` เก็บ ISO date `YYYY-MM-DD` | ช่วง, `to ≥ from` |
| 5 | `select_one` | ประเภท, บริษัทที่จ่าย | `options[]` (label ≥ 1), `display`: `dropdown` / `radio`, `allowOther` (มีช่อง "อื่น ๆ ระบุ") | string | อยู่ใน options |
| 6 | `select_many` | ☐ เพื่อทราบ ☐ เพื่อดำเนินการ | `options[]`, `layout`: `inline` (เรียงในแถวเดียว) / `list`, `minSelected`, `maxSelected` | string[] | จำนวนที่เลือก |
| 7 | `file` | ใบเสนอราคา, รูป | `maxFiles` (1–10, default 5), `accept` (ชุดชนิดไฟล์ ข้อ 8.8) | `[{fileId, name, size, mime}]` | จำนวน, ชนิด, ขนาด |
| 8 | `table` | รายการขอซื้อ | `columns[]` แต่ละคอลัมน์ `{key, label, type: short_text/number/select_one/date, width (สัดส่วน), required}`, `minRows` (default 1), `maxRows` (default 50), `sumColumns[]` (คีย์คอลัมน์ตัวเลขที่จะแสดงผลรวมท้ายตาราง) | `rows: [{key: value}]` | ต่อเซลล์ตามชนิด + จำนวนแถว |
| 9 | `static` | หัวข้อ, คำอธิบาย, เส้นคั่น | `variant`: `heading` / `paragraph` / `line`, `text`, `size` | — (ไม่เก็บ) | — |
| 10 | `auto` | ชื่อผู้ยื่น, แผนก, วันที่ยื่น, เลขที่ | `source`: `submitter_name` / `submitter_department` / `submitter_position` / `submitter_email` / `submitted_at` / `doc_number` / `form_name` | string (เติมตอนส่ง แล้ว**ค้างค่า** ไม่เปลี่ยนตาม) | — |

กฎ validation:
- ตรวจ**ทั้งสองฝั่ง** — client (แสดงทันที) และ server (ปฏิเสธถ้าไม่ผ่าน) ห้ามเชื่อ client อย่างเดียว
- **ร่างไม่ต้องผ่าน validation** บันทึกอะไรก็ได้ · **ส่ง**ต้องผ่านทุกข้อ
- ข้อความ error ภาษาไทย ระบุชื่อฟิลด์ เช่น "กรุณากรอก จำนวนเงิน" "จำนวนเงิน ต้องไม่เกิน 100,000"
- ฟิลด์ `auto` ผู้ยื่นแก้ไม่ได้ (แสดงเป็นข้อความ ไม่ใช่ input)

การแสดงผลบน A4 (โหมดดู/พิมพ์): ทุกชนิดแสดงเป็น**ข้อความบนกระดาษ** ไม่ใช่ input — `select_many` แสดง `☑ เพื่อทราบ ☐ เพื่อดำเนินการ`, `file` แสดงชื่อไฟล์ + ขนาด (บนจอเป็นลิงก์ บนกระดาษเป็นชื่อ), `table` แสดงเป็นตารางมีเส้น + แถวรวม, `date` แสดง พ.ศ.

### 7.5 สายอนุมัติ

ตั้งในแท็บ "สายอนุมัติ" ของตัวออกแบบ โครงสร้าง:

```json
{
  "steps": [
    {
      "id": "s1",
      "name": "ผู้ตรวจสอบ",
      "quorum": 1,
      "deadlineDays": 3,
      "approvers": [
        { "type": "user", "emp_id": "E003" },
        { "type": "relative", "relation": "chief" }
      ]
    },
    {
      "id": "s2",
      "name": "ผู้อนุมัติ",
      "quorum": 2,
      "deadlineDays": null,
      "approvers": [
        { "type": "user", "emp_id": "E001" },
        { "type": "user", "emp_id": "E010" },
        { "type": "submitter_choice", "label": "เรียน", "restrictDepartment": null }
      ]
    }
  ]
}
```

**ขั้น (step)**
- อย่างน้อย 1 ขั้น ไม่จำกัดจำนวนสูงสุด (UI แนะนำไม่เกิน 5)
- `name` ตั้งเอง ไม่ซ้ำกันภายในฟอร์ม — ใช้แสดงในสถานะ "รอ**ผู้ตรวจสอบ**" และในตารางการอนุมัติ
- ขั้นต่อกันเป็น**ลำดับเส้นตรง** ผ่านขั้น 1 ถึงไปขั้น 2 ไม่มีแตกสาย ไม่มีข้าม
- ลาก-สลับลำดับขั้นได้

**ผู้อนุมัติในขั้น** — เลือกได้ 3 วิธี ผสมกันได้ในขั้นเดียว:

| `type` | ความหมาย | resolve เป็นใคร (ตอนส่ง) |
|---|---|---|
| `user` | ระบุตัวคน | คนนั้น |
| `relative` | ตำแหน่งสัมพัทธ์กับผู้ยื่น: `chief` (หัวหน้าโดยตรง) หรือ `department_head` (ผู้จัดการฝ่าย) | จาก API ผังองค์กร (ข้อ 6) |
| `submitter_choice` | ผู้ยื่นเลือกเองตอนส่ง — มี `label` (เช่น "เรียน") และ `restrictDepartment` (จำกัดแผนก หรือ null = ทุกคน) | คนที่ผู้ยื่นเลือก (dropdown ค้นหาได้) |

**กฎ N จาก M (`quorum`)**
- ค่าเริ่มต้นเมื่อสร้างขั้นใหม่: ผู้อนุมัติ 1 คน, `quorum = 1` — กรณีปกติไม่ต้องตั้งอะไร
- `1 ≤ quorum ≤ จำนวนผู้อนุมัติ` — UI ให้เลือกเป็น dropdown "ต้องอนุมัติ [N] จาก M คน" หรือ "ทุกคน"
- ตอน resolve ถ้าคนซ้ำ (เช่น ระบุตัวคน = หัวหน้าโดยตรงพอดี) → **นับเป็นคนเดียว**, M ลดลง, ถ้า `quorum > M` ใหม่ → ปรับ `quorum = M`
- ผู้ยื่นเป็นผู้อนุมัติของตัวเองได้ (ระบบไม่ห้าม แต่ตัวออกแบบแสดงคำเตือนสีเหลืองถ้าใช้ `relative` แล้วอาจเกิดกรณีนี้ — ไม่ต้องตรวจให้ครบทุกกรณี)

**กำหนดเวลา (`deadlineDays`)**
- จำนวน**วันปฏิทิน** ที่ขั้นนี้ควรตอบ นับจากเวลาที่คำร้อง**มาถึงขั้น** (ไม่ใช่ตั้งแต่ส่ง) — `null` = ไม่มีกำหนด
- ผลเมื่อเลย: ป้ายแดง "เกินกำหนด X วัน" + อีเมลเตือน (ข้อ 9) — **ระบบไม่ตัดสินใจแทนใคร** ไม่ auto-approve ไม่ข้ามขั้น ไม่ส่งต่อคนสำรอง (**ทำไม**: เอกสารขออนุมัติเงินต้องมีคนกดเสมอ ถ้ากลัวคนลืมให้ตั้งผู้อนุมัติ 2 คนแบบ 1 จาก 2)

**ตรวจก่อนเผยแพร่**: ทุกขั้นต้องมีผู้อนุมัติ ≥ 1 และ `quorum` ถูกต้อง ไม่งั้นเผยแพร่ไม่ได้

### 7.7 เลขที่เอกสาร

- รูปแบบ `{PREFIX}-{ปี พ.ศ.}-{ลำดับ 4 หลัก}` เช่น `MEMO-2569-0042` — ลำดับรันแยกต่อ prefix ต่อปี เริ่ม `0001` ทุกปีใหม่ เกิน 9999 ให้ยาวขึ้นเอง (`10000`)
- ออกเลข**ตอนกดส่งครั้งแรก**เท่านั้น ร่างไม่มีเลข — ดึงกลับ/ส่งกลับแก้ไข/ส่งใหม่ ใช้**เลขเดิม**
- ต้อง atomic: `counters.findOneAndUpdate({_id: "MEMO-2569"}, {$inc: {seq: 1}}, {upsert: true, returnDocument: "after"})` แล้วเอา `seq` มาใช้ — ห้าม `find` แล้ว `+1` แล้ว `update` (สองคนกดพร้อมกันจะได้เลขซ้ำ)
- เลขที่ออกแล้วไม่นำกลับมาใช้ แม้คำร้องถูกยกเลิก (มีรูโหว่ในลำดับได้ — ปกติของระบบเอกสาร)
- unique index บน `submissions.docNumber` เป็นด่านสุดท้าย

### 7.8 แก้ฟอร์มหลังเผยแพร่ — กฎ snapshot

ฟอร์มที่เผยแพร่แล้ว**แก้ได้ทันที** ไม่ต้องทำเวอร์ชัน แต่มีกฎเดียว:

> **ตอนผู้ยื่นกด "ส่ง" ระบบต้องคัดลอกโครงฟอร์มทั้งหมด (elements + หัวกระดาษ + ชื่อฟอร์ม) และสายอนุมัติที่ resolve แล้ว ฝังลงในเอกสารคำร้อง** — หลังจากนั้นคำร้องไม่อ่านจากฟอร์มอีกเลย

ผล:
- แก้ฟอร์ม (เพิ่ม/ลบ/ย้ายฟิลด์, เปลี่ยนสายอนุมัติ) → คำร้องที่ส่งแล้ว**ไม่กระทบ** แสดงผลเหมือนวันที่ส่งเสมอ
- **ร่าง**ที่ยังไม่ส่ง อ่านจากฟอร์มปัจจุบัน → ถ้าฟอร์มถูกแก้ระหว่างที่มีร่างค้าง ค่าของฟิลด์ที่ถูกลบจะหายจากร่าง (ยอมรับได้ แสดงข้อความ "ฟอร์มมีการเปลี่ยนแปลง กรุณาตรวจสอบ" เมื่อเปิดร่าง)
- ฟอร์มเก็บ `formVersion` (เลขวิ่ง +1 ทุกครั้งที่บันทึก) และคำร้องเก็บ `formVersion` ที่ใช้ตอนส่ง — ไว้ดูย้อนหลังว่าใบไหนใช้โครงรุ่นไหน ไม่ต้องทำ UI diff

**ทำไม**: ง่ายกว่าระบบเวอร์ชันมาก และ MongoDB เหมาะกับการฝังเอกสารแบบนี้พอดี

## 8. คำร้อง

### 8.1 สถานะ

| code | แสดงเป็น | ความหมาย | เป็นสถานะจบ |
|---|---|---|:---:|
| `draft` | ร่าง | ผู้ยื่นยังไม่ส่ง หรือถูกดึงกลับ/ส่งกลับแก้ไข | |
| `pending` | รอดำเนินการ — รอ**{ชื่อขั้น}** (ขั้น k/N) | อยู่ระหว่างสายอนุมัติ | |
| `approved` | อนุมัติครบ | ผ่านทุกขั้น | ✔ |
| `rejected` | ไม่อนุมัติ | มีขั้นที่ตก | ✔ |
| `cancelled` | ยกเลิก | ผู้ยื่นยกเลิกคำร้องที่เคยส่งแล้ว | ✔ |

```
            ┌──────────── ดึงกลับ (ผู้ยื่น) / ส่งกลับแก้ไข (ผู้อนุมัติ) ────────────┐
            ▼                                                                    │
  [draft] ──ส่ง──▶ [pending ขั้น 1] ──ผ่าน──▶ [pending ขั้น 2] ──ผ่าน──▶ … ──▶ [approved]
     │                   │      ▲                  │
     │                   │      └── ดึงกลับ (ผู้อนุมัติขั้น 1) ──┘
     │                   │
     │                   └──ตก──▶ [rejected]
     │
     └──ยกเลิก (เฉพาะร่างที่เคยส่งแล้ว)──▶ [cancelled]        ร่างที่ไม่เคยส่ง: ลบทิ้งได้เลย
```

- สถานะจบ (`approved`/`rejected`/`cancelled`) **เปลี่ยนไม่ได้อีก** ทุกทาง ถ้าต้องการแก้ให้ยื่นใบใหม่ (ระบบมีปุ่ม "ยื่นใหม่จากใบนี้" = สร้างร่างใหม่ copy ค่าที่กรอกมา)
- ผู้ยื่น**ลบ**ร่างที่ไม่เคยส่งได้ (hard delete ไม่มีเลขที่เอกสาร ไม่มีใครเคยเห็น) — ร่างที่เคยส่งแล้วต้อง "ยกเลิก" (เก็บไว้เป็นประวัติ)

### 8.2 การกระทำทั้งหมด

| การกระทำ | ใครทำได้ | ทำได้เมื่อ | ผล |
|---|---|---|---|
| **บันทึกร่าง** | ผู้ยื่น | `draft` | เก็บค่าที่กรอก ไม่ validate |
| **ส่ง** | ผู้ยื่น | `draft` + validation ผ่าน | resolve ผู้อนุมัติทุกขั้น, snapshot, ออกเลขที่ (ครั้งแรก), `rounds` +1, → `pending` ขั้น 1, แจ้งผู้อนุมัติขั้น 1 |
| **ดึงกลับ** (ผู้ยื่น) | ผู้ยื่น | `pending` ขั้น 1 **และ**ยังไม่มีใครในขั้น 1 กดอะไรเลยในรอบนี้ | → `draft` บันทึกเหตุการณ์ "ดึงกลับ" |
| **ดึงกลับ** (ผู้อนุมัติ) | ผู้อนุมัติที่**เคยกด "อนุมัติ"** ในขั้น k รอบนี้ | ยังไม่มีใครในขั้นถัดจาก k กดอะไรเลย (คำร้องอาจอยู่ขั้น k หรือ k+1) | ถอนการอนุมัติของตัวเอง → คำร้องกลับมา `pending` ขั้น k (ถ้าอยู่ k+1) |
| **อนุมัติ** | ผู้อนุมัติของขั้นปัจจุบันที่ยังไม่ได้กดในรอบนี้ | `pending` | บันทึก; ถ้าอนุมัติ ≥ N → ไปขั้นถัดไป (หรือ `approved` ถ้าขั้นสุดท้าย) แจ้งคนที่เกี่ยวข้อง |
| **ไม่อนุมัติ** | ผู้อนุมัติของขั้นปัจจุบัน (ยังไม่ได้กด) | `pending` | บันทึก; ถ้าไม่มีทางได้ N แล้ว (8.3) → `rejected` แจ้งผู้ยื่น |
| **ส่งกลับแก้ไข** | ผู้อนุมัติของขั้นปัจจุบัน | `pending` | → `draft` ทันที (ไม่ต้องรอเสียง) การกดทั้งหมดของรอบนี้ถือเป็นโมฆะ แจ้งผู้ยื่นพร้อมข้อความ |
| **ยกเลิก** | ผู้ยื่น | `draft` ที่เคยส่งแล้ว | → `cancelled` |
| **ลบร่าง** | ผู้ยื่น | `draft` ที่ไม่เคยส่ง | hard delete |
| **เพิ่มความเห็น** | ผู้ยื่น + ผู้อนุมัติทุกขั้น + ผู้ดูแลฟอร์ม/admin | ทุกสถานะ | ต่อท้ายไทม์ไลน์ ไม่เปลี่ยนสถานะ |

ทุกการกดของผู้อนุมัติ (อนุมัติ/ไม่/ส่งกลับ/ดึงกลับ) มี**ช่องความเห็น** (ไม่บังคับ ยกเว้น "ไม่อนุมัติ" และ "ส่งกลับแก้ไข" **บังคับ ≥ 5 ตัวอักษร**) และ**แนบไฟล์ได้** (ข้อ 8.8)

### 8.3 กฎ N จาก M — สูตรเดียว

ในขั้นที่มีผู้อนุมัติ M คน ต้องการ N เสียง:

```
approvals = จำนวนคนที่กด "อนุมัติ" ในขั้นนี้ รอบนี้
rejections = จำนวนคนที่กด "ไม่อนุมัติ" ในขั้นนี้ รอบนี้

ผ่านขั้น  เมื่อ  approvals >= N
ตกขั้น    เมื่อ  rejections > M - N        (= ไม่มีทางได้ครบ N แล้ว)
ไม่งั้น   รอคนที่เหลือ
```

| ตั้งค่า | ผ่านเมื่อ | ตกเมื่อ |
|---|---|---|
| 1 จาก 1 | คนเดียวอนุมัติ | คนเดียวไม่อนุมัติ |
| 1 จาก 3 | ใครก็ได้ 1 คนอนุมัติ | **ทั้ง 3 คน**ไม่อนุมัติ |
| 2 จาก 3 | 2 คนอนุมัติ | 2 คนไม่อนุมัติ |
| 3 จาก 3 | ครบ 3 คน | คนแรกที่ไม่อนุมัติ |

- เขียนเป็น**ฟังก์ชัน pure** `evaluateStep(step, decisions) → 'passed' | 'failed' | 'waiting'` แล้วเขียน unit test ครอบทั้ง 4 แถวข้างบน + กรณีดึงกลับ
- เมื่อผ่านขั้น: คนที่ยังไม่ได้กดในขั้นนั้น**ไม่ต้องกดแล้ว** งานหายจากกล่องงานของเขา แต่ยังเปิดดูได้ (ตารางการอนุมัติแสดง "— ไม่ต้องกด (ครบเสียงแล้ว)")
- ตัดสินโดยเทียบกับ M **หลัง dedup** (7.5)

### 8.4 ดึงกลับ — กฎละเอียด

หลักการเดียว: **"คนที่กระทำล่าสุด ถอนได้ ตราบใดที่คนถัดไปยังไม่ได้กระทำ"** — ผู้ยื่นถือเป็น "ขั้น 0"

ตัวอย่างสาย 3 ขั้น (A → B → C แต่ละขั้น 1 จาก 1):

| สถานการณ์ | ใครดึงได้ | ผล |
|---|---|---|
| ส่งแล้ว A ยังไม่กด | ผู้ยื่น | กลับเป็นร่าง |
| A อนุมัติแล้ว B ยังไม่กด | **A เท่านั้น** (ผู้ยื่นดึงไม่ได้แล้ว) | ถอนของ A → กลับมารอ A ใหม่ (A จะอนุมัติซ้ำ/ไม่อนุมัติ/ส่งกลับแก้ไข ก็ได้) |
| A, B อนุมัติแล้ว C ยังไม่กด | **B เท่านั้น** | ถอนของ B → กลับมารอ B |
| C อนุมัติแล้ว (= approved) | ไม่มีใคร | สถานะจบ |
| A ไม่อนุมัติ (= rejected) | ไม่มีใคร | สถานะจบ — การกดที่ทำให้จบสถานะ ถอนไม่ได้ |

ขั้นที่มีหลายคน (2 จาก 3: A1, A2, A3):

| สถานการณ์ | ใครดึงได้ | ผล |
|---|---|---|
| A1 อนุมัติ, ยังไม่ครบ 2 | A1 | ถอนของตัวเอง approvals กลับเป็น 0 |
| A1, A2 อนุมัติ → ผ่านขั้น อยู่ขั้น B, B ยังไม่กด | A1 **หรือ** A2 (คนละครั้ง ถอนเฉพาะของตัวเอง) | approvals เหลือ 1 < 2 → คำร้องกลับมา `pending` ขั้น A |
| A1 ไม่อนุมัติ (ยังไม่ตก เพราะ 1 ≤ 3−2) | A1 | ถอนของตัวเอง |

- ดึงกลับ**ไม่ใช่การกลับไปหาผู้ยื่น** (นั่นคือ "ส่งกลับแก้ไข") — ผู้อนุมัติที่ดึงกลับแล้วอยากให้ผู้ยื่นแก้ ให้กด "ส่งกลับแก้ไข" ต่อ
- การดึงกลับทุกครั้งบันทึกในไทม์ไลน์ (ใคร เมื่อไหร่ ความเห็น) และ**การอนุมัติที่ถูกถอนยังอยู่ในประวัติ**แต่ทำเครื่องหมาย "ถูกดึงกลับ"
- ผู้ยื่นดึงกลับแล้วส่งใหม่ = **รอบใหม่ เริ่มขั้น 1** เสมอ (ในกรณีนี้ยังไม่มีใครกดอยู่แล้วจึงไม่มีอะไรเสีย)

### 8.5 ส่งกลับแก้ไข / ไม่อนุมัติ / ส่งใหม่

- **ส่งกลับแก้ไข**: ผู้อนุมัติคนเดียวในขั้นปัจจุบันกดได้ทันที มีผลทันที (ไม่ต้องรอเสียง) → คำร้องกลับเป็น `draft` การกดทุกอย่างในรอบนี้ (ทุกขั้นที่ผ่านมา) ถือเป็นโมฆะแต่เก็บไว้ในประวัติรอบนั้น ผู้ยื่นแก้แล้วส่งใหม่ = **รอบใหม่ เริ่มขั้น 1** (**ทำไม**: เนื้อหาเปลี่ยน คนที่เคยอนุมัติต้องเห็นของใหม่)
- **ไม่อนุมัติ**ที่ทำให้ตกขั้น → `rejected` จบ ผู้ยื่นแก้ไม่ได้ ต้อง "ยื่นใหม่จากใบนี้" (ได้เลขที่ใหม่)
- แต่ละ**รอบ**เก็บแยก: `rounds: [{round: 1, submittedAt, endedAt, endedBy: 'recalled'|'returned'|'rejected'|'approved', steps: [...]}]` — หน้าคำร้องแสดงรอบปัจจุบันเต็ม รอบเก่าย่อไว้ กดขยายดูได้
- ตอนส่งใหม่ ระบบ **resolve ผู้อนุมัติใหม่** (คนอาจเปลี่ยน เช่น หัวหน้าเปลี่ยน) และ snapshot ใหม่

### 8.6 กำหนดเวลาและ "รอมาแล้ว"

- ทุกขั้นบันทึก `enteredAt` (เวลาที่คำร้องมาถึงขั้นนี้ในรอบนี้) — เมื่อดึงกลับมาที่ขั้น k ให้ตั้ง `enteredAt` ใหม่
- **รอมาแล้ว** = เวลาปัจจุบัน − `enteredAt` ของขั้นปัจจุบัน แสดงหน่วยตามจริง:

| ช่วง | แสดง |
|---|---|
| < 1 ชม. | "รอมาแล้ว 25 นาที" |
| < 1 วัน | "รอมาแล้ว 5 ชั่วโมง 10 นาที" |
| < 30 วัน | "รอมาแล้ว 3 วัน 4 ชั่วโมง" |
| < 365 วัน | "รอมาแล้ว 2 เดือน 12 วัน" |
| ≥ 365 วัน | "รอมาแล้ว 1 ปี 3 เดือน" |

- แสดง 2 หน่วยเสมอ (หน่วยใหญ่ + หน่วยรอง) ยกเว้น < 1 ชม. แสดงนาทีอย่างเดียว; < 1 นาที แสดง "เมื่อสักครู่"
- แสดง**รวมทั้งใบ**ด้วย: เวลาปัจจุบัน − `submittedAt` ของรอบปัจจุบัน
- **เกินกำหนด** = ขั้นมี `deadlineDays` และ `now > enteredAt + deadlineDays` → ป้ายแดง "เกินกำหนด 2 วัน" ทั้งในกล่องงาน รายการ และหน้าคำร้อง
- เขียน `humanizeDuration(ms)` เป็นฟังก์ชัน pure + unit test ที่ขอบทุกช่วง (59 นาที / 60 นาที / 23:59 / 24:00 / 29 วัน / 30 วัน / 364 / 365)
- ค่าทั้งหมด**คำนวณตอนแสดง** ไม่เก็บลง DB (จะเก่าทันที)

- ทดสอบด้วย "บันทึกเป็น PDF" ใน Chrome — ต้องได้ PDF ที่หน้าตาเหมือนบนจอ 100% ไม่มีเลื่อนตำแหน่ง ไม่มีขอบเกิน ฟอนต์ไทยถูกต้อง
- ลายน้ำสถานะที่มุมกระดาษ: "ร่าง", "รอดำเนินการ", "ไม่อนุมัติ", "ยกเลิก" — ใบที่ `approved` ไม่มีลายน้ำ (**ทำไม**: กันคนพิมพ์ร่างไปใช้เหมือนของอนุมัติแล้ว)

**มือถือ**
- หน้า A4 (กรอก/ดู) บนมือถือ: **ย่อทั้งกระดาษให้พอดีความกว้างจอ** (`transform: scale`) + ซูมนิ้วได้ (pinch) — **ไม่ทำ layout แยก** หน้าตาเหมือน desktop เป๊ะ
- โหมดกรอกบนมือถือ: แตะช่องแล้วซูมเข้าอัตโนมัติพอให้พิมพ์ได้ (หรือเปิด sheet กรอกด้านล่างสำหรับช่องนั้น — เลือกทางใดทางหนึ่งแล้วทำให้ดี)
- ส่วนที่**ไม่ใช่กระดาษ** (กล่องงาน, รายการ, ปุ่มอนุมัติ, ไทม์ไลน์) เป็น responsive ปกติ ปุ่มอนุมัติ/ไม่อนุมัติ/ส่งกลับ ต้องกดง่ายบนจอ 375px
- ตัวออกแบบฟอร์ม: desktop เท่านั้น (7.2)

### 8.8 ไฟล์แนบ

| กฎ | ค่า |
|---|---|
| ขนาดต่อไฟล์ | ≤ **10 MB** (`MAX_FILE_MB`) — ตรวจที่ server ด้วย ไม่ใช่แค่ client |
| จำนวนต่อฟิลด์ | ≤ `maxFiles` ของฟิลด์ (สูงสุด 10) · ไฟล์ของผู้อนุมัติ ≤ 10 ต่อการกด 1 ครั้ง |
| ชนิดที่รับ | `pdf, jpg, jpeg, png, gif, webp, xlsx, xls, docx, doc, csv, txt` — ตรวจทั้ง**นามสกุล**และ **magic bytes** (เช่น `%PDF`, `\xFF\xD8`) ไม่เชื่อ `Content-Type` ที่ client ส่ง · ปฏิเสธ `exe, bat, sh, js, html, svg, zip, rar` |
| ที่เก็บ | `{UPLOAD_DIR}/{yyyy}/{mm}/{uuid}.{ext}` — **ชื่อไฟล์บน disk เป็น uuid เสมอ** ชื่อเดิมเก็บใน DB (กัน path traversal, ชื่อไทย, ชื่อซ้ำ) |
| ข้อมูลใน DB | `{fileId, originalName, size, mime, ext, path, uploadedBy(emp_id), uploadedAt, scope: 'field'|'decision', elementId?, stepId?}` |
| ดาวน์โหลด | ผ่าน route `GET /files/{fileId}` เท่านั้น — ตรวจ session + ตรวจว่าผู้ใช้เกี่ยวข้องกับคำร้องนั้น (ข้อ 4) → stream ไฟล์ ใส่ `Content-Disposition: attachment; filename*=UTF-8''...` (รูปภาพเปิด inline ได้) · **ห้าม**ให้ web server serve โฟลเดอร์ upload ตรง ๆ |
| ลบ | ผู้ยื่นลบไฟล์ได้เฉพาะตอน `draft` · ไฟล์ของผู้อนุมัติลบไม่ได้หลังกด · ลบ = ลบจาก DB + disk |
| ไฟล์กำพร้า | อัปโหลดสำเร็จแต่ผู้ใช้ปิดหน้าโดยไม่บันทึก → job วันละครั้งลบไฟล์บน disk ที่ไม่มีการอ้างถึงใน DB และอายุ > 24 ชม. |
| upload flow | อัปโหลดทีละไฟล์ทันทีที่เลือก (ไม่รอกดบันทึก) → ได้ `fileId` → เก็บใน state ของฟอร์ม → บันทึกร่าง/ส่ง เขียน `fileId` ลงคำร้อง · แสดง progress bar |

แยกให้ชัด: **ไฟล์ของผู้ยื่น**อยู่ในฟิลด์ `file` บนกระดาษ · **ไฟล์ของผู้อนุมัติ**อยู่ในไทม์ไลน์/ตารางการอนุมัติ ไม่ปนกัน

### 8.9 ป้องกันการกดชนกัน (concurrency)

คำร้องทุกใบมีฟิลด์ `version` (เริ่ม 1, +1 ทุกครั้งที่เปลี่ยน) ทุกการกระทำในข้อ 8.2 ต้องทำแบบนี้:

```js
const result = await submissions.findOneAndUpdate(
  {
    _id: id,
    version: expectedVersion,          // เวอร์ชันที่ผู้ใช้เห็นตอนโหลดหน้า (ส่งมากับ request)
    status: 'pending',                 // เงื่อนไขว่าสถานะยังเป็นที่คาดไว้
    'current.stepIndex': k,
  },
  {
    $push: { 'rounds.$[r].steps.$[s].decisions': decision },
    $set: { /* สถานะใหม่ที่คำนวณแล้ว */ },
    $inc: { version: 1 },
  },
  { returnDocument: 'after', arrayFilters: [...] }
);
if (!result.value) {
  // มีคนกดตัดหน้า หรือสถานะเปลี่ยนไปแล้ว
  return res.status(409).json({ error: 'คำร้องนี้เพิ่งมีการเปลี่ยนแปลง กรุณาโหลดหน้าใหม่' });
}
```

- ฝั่งหน้าเว็บ: เมื่อได้ 409 → โหลดข้อมูลใหม่ + แสดงข้อความ ไม่ต้องทำอะไรซับซ้อน
- ขั้นตอน: **อ่านเอกสาร → คำนวณสถานะใหม่ใน memory (ด้วย `evaluateStep`) → เขียนกลับด้วยเงื่อนไข version** — ถ้าระหว่างนั้นมีคนอื่นเขียน เงื่อนไขจะไม่ match เอง
- นี่คือเหตุผลที่ "คำร้อง = เอกสารเดียว" — ทุกอย่างที่ต้องเปลี่ยนพร้อมกันอยู่ในเอกสารเดียว จึง atomic โดยไม่ต้องมี transaction
- ทดสอบ: เปิดคำร้อง "1 จาก 2" ใน 2 browser (login คนละคน) กดอนุมัติพร้อมกัน → คนหนึ่งสำเร็จ อีกคนได้ 409 และตารางการอนุมัติมีการอนุมัติ**ครั้งเดียว**

### 8.10 เดินครบหนึ่งรอบ — ตัวอย่างจริง

ฟอร์ม "MEMO ขออนุมัติ" prefix `MEMO`, สาย 2 ขั้น: ขั้น 1 "ผู้ตรวจสอบ" = หัวหน้าโดยตรงของผู้ยื่น (1 จาก 1) → ขั้น 2 "ผู้อนุมัติ" = ผู้ยื่นเลือกเอง ("เรียน")

1. **สมชาย (ฝ่ายไอที)** เลือกฟอร์ม กรอก เรื่อง "ขอเติมเงิน OpenRouter" เรียน "ฝ่ายบัญชี" ติ๊ก ☑ เพื่อการอนุมัติ รายละเอียด ตาราง 1 รายการ 100 USD แนบใบแจ้งยอด กด **บันทึกร่าง** → `draft` ยังไม่มีเลขที่
2. กด **ส่ง** → validation ผ่าน → resolve: ขั้น 1 = `chief` ของสมชาย = นิมิต; ขั้น 2 = สมชายเลือก "ศรัญญา" → snapshot → `docNumber = MEMO-2569-0042`, `submittedAt` → `pending` ขั้น 1/2 รอผู้ตรวจสอบ → อีเมลถึงนิมิต
3. **นิมิต** เห็นในกล่องงาน "รอมาแล้ว 2 ชั่วโมง" เปิดดู A4 กด **อนุมัติ** ความเห็น "ตรวจแล้ว" → ขั้น 1 ผ่าน (1 ≥ 1) → `pending` ขั้น 2/2 รอผู้อนุมัติ → อีเมลถึงศรัญญา, แจ้งสมชายในระบบ
4. นิมิตนึกได้ว่าลืมดูยอด กด **ดึงกลับ** (ศรัญญายังไม่กด) → ถอนการอนุมัติ → `pending` ขั้น 1/2 อีกครั้ง `enteredAt` ใหม่
5. นิมิตกด **ส่งกลับแก้ไข** "ระบุเดือนที่ใช้ด้วย" → `draft` รอบที่ 1 จบ (`endedBy: returned`) → อีเมลถึงสมชาย
6. สมชายแก้ กด **ส่ง** → รอบที่ 2 เลขที่เดิม `MEMO-2569-0042` เริ่มขั้น 1 ใหม่ → นิมิตอนุมัติ → ศรัญญาอนุมัติ → `approved`
7. สมชายกด **พิมพ์** ได้ A4 ที่มีตารางการอนุมัติของรอบที่ 2 ไม่มีลายน้ำ; ไทม์ไลน์ด้านข้างแสดงรอบที่ 1 ที่ถูกส่งกลับ

ทั้ง 7 ขั้นนี้คือ**เกณฑ์ตรวจรับหลัก** — ถ้าทำได้ครบและถูกต้อง ระบบใช้จริงได้

### 9.2 กฎ

- เขียนเป็นชั้นเดียว `notify(event)` ที่ภายในเรียก `inAppChannel` + `emailChannel` — เพิ่ม LINE ทีหลังโดยเพิ่ม channel เดียว ไม่แตะ logic ธุรกิจ
- **การส่งอีเมลห้ามบล็อกการกดปุ่ม**: บันทึกลง collection `notifications` (`{to, type, subject, body, link, status: 'queued', attempts, createdAt, sentAt?}`) แล้ว worker/interval ส่งทีหลัง ล้มเหลว retry 3 ครั้ง ห่าง 1/5/15 นาที แล้ว mark `failed` — อีเมลล่ม ระบบต้องยังใช้ได้
- `MAIL_MODE=console` พิมพ์อีเมลลง log แทนส่งจริง (ใช้ตอน dev)
- อีเมล: ข้อความล้วน (plain text) พอ ไม่ต้อง HTML สวย หัวข้อ `[its-forms] MEMO-2569-0042 รอคุณอนุมัติ — ขอเติมเงิน OpenRouter` เนื้อหา: ชื่อฟอร์ม, เรื่อง, ผู้ยื่น, ขั้น, รอมาแล้ว, **ลิงก์ตรงไปหน้าคำร้อง** (`{APP_URL}/submissions/{id}`)
- ในระบบ: กระดิ่ง + ตัวเลขแดง, รายการ 30 อันล่าสุด, กดแล้ว mark อ่าน, refresh ทุก 30 วินาที (polling)
- ไม่ต้องมีหน้าตั้งค่า "ไม่รับอีเมล" ใน v1

### 10.3 `/submissions/new?form=…` และ `/submissions/{id}/edit` กรอกคำร้อง — ผู้ยื่น

- แสดง A4 โหมด `edit` ตรงกลาง, แถบขวา (desktop) / ล่าง (มือถือ): ปุ่ม **บันทึกร่าง**, **ส่ง**, **ลบร่าง**; ถ้าสายอนุมัติมี `submitter_choice` แสดงช่องเลือกคนตรงนี้ (มี label เช่น "เรียน") ก่อนส่ง

- กดส่ง → แสดง**หน้ายืนยัน**: สรุปสายอนุมัติที่ resolve แล้ว "ขั้น 1 ผู้ตรวจสอบ: นิมิต คงอำนาจ → ขั้น 2 ผู้อนุมัติ: ศรัญญา ประทุม" ให้ผู้ยื่นเห็นว่าใบจะเดินไปหาใคร → ยืนยัน
- validation error แสดงที่ฟิลด์บนกระดาษ + สรุปด้านบน "กรุณาตรวจสอบ 3 รายการ"

### 10.4 `/submissions/{id}` ดูคำร้อง — คนที่เกี่ยวข้อง

- ซ้าย/กลาง: A4 โหมด `view` (ลายน้ำตามสถานะ)
- ขวา (desktop) / ล่าง (มือถือ): **แถบสถานะ** (สถานะ, ขั้น, รอมาแล้ว, เกินกำหนด) → **ปุ่มตามบทบาทและสถานะ** (ตารางข้อ 8.2 — ปุ่มที่ทำไม่ได้ต้องไม่แสดง ไม่ใช่แสดงแล้ว error) → **ไทม์ไลน์** ทุกเหตุการณ์ทุกรอบ (ส่ง, อนุมัติ, ดึงกลับ, ส่งกลับ, ความเห็น, ไฟล์ของผู้อนุมัติ) เรียงเวลา รอบเก่าย่อ → ช่องเพิ่มความเห็น
- ปุ่ม **พิมพ์** / **พิมพ์พร้อมประวัติ** / **ยื่นใหม่จากใบนี้**
- กด อนุมัติ/ไม่อนุมัติ/ส่งกลับ/ดึงกลับ → dialog ยืนยัน มีช่องความเห็น (+ บังคับตาม 8.2) + แนบไฟล์ → ส่งพร้อม `version`

### 10.7 `/manage/forms/{id}/submissions` คำร้องทั้งหมดของฟอร์ม — ผู้ดูแลฟอร์ม

### 10.8 `/admin/settings` ตั้งค่าระบบ — admin

- **หัวกระดาษ**: รายการ (ชื่อ, โลโก้ upload, ชื่อบริษัท, ที่อยู่/โทร) เพิ่ม/แก้/ปิดใช้

## 12. ความปลอดภัย (ขั้นต่ำที่ต้องมี)

1. **ทุก route ตรวจ session** ยกเว้น `/auth/*`, health check, static assets — ใช้ middleware กลางตัวเดียว ไม่ใส่ทีละ route
2. **ตรวจสิทธิ์ที่ server ทุกครั้ง** ตามตารางข้อ 4 และ 8.2 — เดา id คำร้องของคนอื่นแล้วเปิดต้องได้ 403; กด "อนุมัติ" ผ่าน API ตรง ๆ โดยไม่ใช่ผู้อนุมัติของขั้นนั้นต้องได้ 403
3. **ป้องกัน XSS**: label/ค่าที่ผู้ใช้กรอก/ความเห็น ทุกอย่างที่แสดงบนหน้าต้อง escape — ทดสอบด้วยการกรอก `<script>alert(1)</script>` ในเรื่อง แล้วเปิดดู/พิมพ์
4. **CSRF**: ทุก request ที่เปลี่ยนข้อมูลเป็น POST/PUT/DELETE + CSRF token (หรือ SameSite=Lax cookie + ตรวจ `Origin` header)
5. **ไฟล์**: ตาม 8.8 ทั้งหมด — ห้าม serve โฟลเดอร์ upload ตรง, ชื่อไฟล์ uuid, ตรวจ magic bytes
6. **ห้ามมี secret ในโค้ด/log** — ห้าม log token, session id, เนื้อหาอีเมลที่มีลิงก์ (log แค่ว่าส่งถึงใครสำเร็จไหม)
7. **Rate limit** `/auth/*` และ `/files/*` แบบง่าย (เช่น 60 ครั้ง/นาที/IP) พอ
8. HTTP security headers พื้นฐาน (`X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy`) — ใช้ library มาตรฐานของ framework
9. Dependencies: รัน `npm audit` (หรือเทียบเท่า) ก่อนส่งมอบแต่ละก้อน ไม่มี critical/high ค้าง

## 17. กติกาการทำงาน

1. **ติดตามงานผ่าน GitHub Issues** ของ repo — ทุกงานย่อยเป็น issue ที่มี "ทำอะไร" + "เสร็จเมื่อไหร่ถือว่าเสร็จ" ก่อนเริ่มเขียนโค้ด · ปิด issue ด้วย commit/PR ที่อ้างถึงมัน (`closes #12`)
2. **commit + push ทุกวันที่ทำงาน** ข้อความ commit บอกว่าทำอะไร ทำไม (ภาษาไทยได้) — วันที่ไม่มี commit = วันที่ไม่ได้ทำงาน
3. **ทำงานบน branch แยกต่อ issue** → เปิด Pull Request → ฝ่ายไอที review → merge · PR ต้องบอกวิธีทดสอบ
4. **วันอังคาร (เข้าไซต์)** = demo ของที่รันได้จริง 15 นาที + review + merge + งานที่ต้องอยู่ในเครือข่ายบริษัท (SSO จริง, ทดสอบกับ API จริง, ดูไอที deploy) — เตรียมของให้พร้อมก่อนมา
   **การส่งงาน = push ขึ้น GitHub เท่านั้น** คุณไม่ deploy เอง ไม่มีสิทธิ์ server · ไอที deploy จาก branch `main` (ผ่าน PR ที่ review แล้ว) และ tag เวอร์ชัน `v0.1` … `v1.0` ตามก้อนที่ส่งมอบ · ห้าม push ตรงเข้า `main`
5. **ติดปัญหาเกิน 2 ชั่วโมง = ถาม** ทางช่องทางที่ตกลงกัน โดยแนบ: ทำอะไรอยู่, ลองอะไรไปแล้ว, error เต็ม ๆ — อย่านั่งเดาต่อ
6. **AI เขียนได้ แต่คุณต้องอธิบายได้** — ตอน demo ฝ่ายไอทีจะสุ่มชี้โค้ดแล้วถามว่าทำงานอย่างไร ทำไมเขียนแบบนี้ ถ้าตอบไม่ได้ให้กลับไปทำความเข้าใจก่อน merge
7. **ห้ามข้ามเอกสาร**: ถ้าจะทำต่างจากที่เขียนไว้ ให้เปิด issue อธิบายเหตุผลก่อน ไม่ทำเงียบ ๆ · เอกสารนี้แก้ได้เมื่อตกลงกัน และการแก้ต้อง commit ลง repo (เก็บ `docs/requirement.md` ไว้ใน repo ด้วย)
8. **ไม่มีข้อมูลจริงในเครื่องคุณ** — ห้าม export/copy DB จริง ไฟล์แนบจริง หรือรายชื่อพนักงานจริงมาไว้ที่บ้าน ใช้ mock + บัญชีทดสอบเท่านั้น

เมื่อพิมพ์ต้องดูใกล้เคียง MEMO กระดาษเดิมมากพอที่ฝ่ายบัญชีรับได้โดยไม่ต้องอธิบาย

## ภาคผนวก C — คำถามที่คนเริ่มใหม่มักถาม

**AI แนะนำให้ใช้ Prisma / TypeORM / transaction** → ไม่ใช้ ดูข้อ 3.2 บอก AI ว่า "MongoDB 5 standalone, no replica set, no transactions, use the official driver"

**ควรทำ realtime (websocket) ให้กล่องงานเด้งเองไหม** → ไม่ polling 30 วินาทีพอ change streams ใช้ไม่ได้อยู่แล้ว

**ต้องเก็บ token ของ sellcenter ไว้ไหม** → ไม่ ใช้ครั้งเดียวตอน login แล้วสร้าง session ของเราเอง

**ถ้าหัวหน้าของผู้ยื่นลาออกกลางทาง คำร้องที่ค้างอยู่จะทำอย่างไร** → v1 ไม่มีมอบสิทธิ์แทน ให้ผู้ยื่นดึงกลับ (ถ้ายังทำได้) หรือยกเลิกแล้วยื่นใหม่ ระบบจะ resolve หัวหน้าคนใหม่ · ถ้าดึงไม่ได้ admin ต้องประสานเอง — เป็นข้อจำกัดที่รู้อยู่แล้ว

**ทำไมไม่ทำ layout มือถือแยกสำหรับ A4** → เพราะเอกสารต้อง "หน้าตาเดียวกันทุกที่" การย่อ+ซูมทำให้ทุกคนเห็นสิ่งเดียวกับที่จะพิมพ์ออกมา และประหยัดงานไปครึ่งหนึ่ง

**ควรแยกเป็น microservice / แยก frontend-backend คนละ repo ไหม** → ไม่ ระบบเดียว repo เดียว container เดียว (+ mongo) ง่ายต่อการ deploy และ review

**ใช้ UI library อะไรดี** → อะไรก็ได้ที่คุณและ AI ถนัด ขอแค่ส่วนกระดาษ A4 คุมด้วย CSS ของคุณเอง (หน่วย mm, `@media print`) ไม่พึ่ง component ของ library ที่ควบคุมตอนพิมพ์ไม่ได้

**จะรู้ได้อย่างไรว่า "เสร็จ"** → ทำเช็คลิสต์ก้อนนั้นในข้อ 14 ครบ + เกณฑ์ที่เกี่ยวข้องในข้อ 15 ผ่านโดยคุณทดสอบเองก่อน แล้ว demo วันอังคาร

## ภาคผนวก D — สเปก API ผังองค์กร (Org Directory API) ฉบับเต็ม

API นี้อยู่บน sellcenter ฝ่ายไอทีเป็นคนดูแล คุณเป็น**ผู้เรียก**อย่างเดียว · ถ้าของจริงตอบไม่ตรงกับที่เขียนไว้ตรงนี้ ให้แจ้งฝ่ายไอที (ถือว่าเอกสารหรือ API ผิด ไม่ใช่ให้คุณ workaround)

### D.1 พื้นฐาน

| เรื่อง | ค่า |
|---|---|
| Base URL | `{SELLCENTER_URL}` (ตัวเดียวกับ SSO) |
| รูปแบบ | REST, JSON, UTF-8, อ่านอย่างเดียว (มีแต่ `GET`) |
| Auth | header `x-service-token: {ORG_API_TOKEN}` **หรือ** `Authorization: Bearer {ORG_API_TOKEN}` — เลือกอย่างใดอย่างหนึ่ง |
| Token | service token ที่ฝ่ายไอทีสร้างให้ระบบนี้โดยเฉพาะ scope `org:read` · เก็บใน `.env` เท่านั้น · **ห้ามส่งไปหน้า browser** (เรียกจาก server ของคุณเท่านั้น) |
| Cache | ทุก response มี `Cache-Control: no-store` = server ไม่ cache ให้ คุณ**ต้อง cache เอง** 10 นาที (ข้อ 6) |
| ปริมาณ | ไม่มี pagination — พนักงานทั้งบริษัทมาในครั้งเดียว (หลักสิบถึงร้อยคน) |
| Encoding | ชื่อภาษาไทยเป็น UTF-8 ปกติ |

### D.2 โครง response กลาง

สำเร็จ:
```json
{ "success": true, "count": 12, "data": [ … ] }        // สำหรับรายการ
{ "success": true, "data": { … } }                     // สำหรับรายเดียว
```

ล้มเหลว:
```json
{ "success": false, "error": "ข้อความ" }
```

| HTTP | `error` | ความหมาย | คุณควรทำอะไร |
|---|---|---|---|
| 401 | `Missing service token (x-service-token or Authorization: Bearer)` | ไม่ได้ส่ง header | bug ฝั่งคุณ — เช็ค `.env` โหลดถูกไหม |
| 403 | `Token not found or inactive` / `Token expired` / `Insufficient scope` | token ผิด/ถูกยกเลิก/หมดอายุ/ไม่มี scope `org:read` | แจ้งไอทีขอ token ใหม่ · ระหว่างนั้นใช้ cache |
| 404 | `Employee not found` | ไม่มี `emp_id` นี้ | แสดง "ไม่พบพนักงาน" — เกิดได้กับคำร้องเก่าที่คนถูกลบ |
| 500 | ข้อความ error | sellcenter มีปัญหา (เช่น DB itime ล่ม) | ใช้ cache + แถบเตือน "ข้อมูลพนักงานอาจไม่เป็นปัจจุบัน" · retry รอบ sync ถัดไป |
| (เชื่อมต่อไม่ได้ / timeout) | — | sellcenter ล่มหรือเครือข่ายมีปัญหา | เหมือน 500 · ตั้ง timeout 5 วินาที อย่ารอนาน |

**หลักการ**: API นี้ล่ม → ระบบคุณต้อง**ยังยื่น/อนุมัติได้** จากข้อมูลใน `users` ที่ sync ไว้ · สิ่งเดียวที่ทำไม่ได้คือ resolve `relative` สำหรับคนที่ไม่เคย sync

### D.6 ฟิลด์ของ employee — ความหมายและกฎ

| ฟิลด์ | ชนิด | ว่าง/null ได้ | ความหมาย |
|---|---|:---:|---|
| `id` | string | ✘ | รหัสภายในของระบบ itime — **ตรงกับ `sub` จาก `/system81/userinfo`** ใช้ผูกตัวตนหลัง SSO |
| `emp_id` | string | ✘ | รหัสพนักงาน — **คีย์หลักที่ใช้อ้างถึงคนทุกที่ในระบบคุณ** (`chief`, `head`, path ของ D.4, ผู้อนุมัติในสาย) |
| `email` | string | ✘ | ตัวพิมพ์เล็กเสมอ · = `username` ที่ `/system81/userinfo` คืน |
| `name` | string | ✘ | ชื่อเต็ม (`first_name last_name`; ถ้าไม่มีใช้ชื่อที่ itime เก็บ; ถ้าไม่มีอีกใช้ email) — ใช้ตัวนี้แสดงผลเสมอ |
| `first_name` / `last_name` | string | ว่างได้ | แยกไว้เผื่อเรียง/ค้น |
| `nickname` | string | ว่างได้ | ชื่อเล่น — แสดงต่อท้ายชื่อในวงเล็บได้ถ้าไม่ว่าง |
| `picture` | string \| null | null ได้ | path หรือ URL รูปตามที่ itime เก็บ — อาจเป็น path สัมพัทธ์ ไม่รับประกันว่าเปิดจากระบบคุณได้ **ไม่ต้องใช้ใน v1** |
| `department` | object \| null | null ได้ | `{ id, name }` — `name` อาจว่าง `""` ถ้า id ไม่ตรงกับแผนกใดใน D.5 (ข้อมูล itime ไม่สมบูรณ์) |
| `position` | object \| null | null ได้ | `{ id, name }` — เช่นเดียวกัน |
| `chief` | object \| null | null ได้ | **หัวหน้าโดยตรง** `{ emp_id, name }` — `name` ยังมีค่าแม้หัวหน้าลาออกแล้ว; `null` = ไม่มีหัวหน้า (เช่น ผู้บริหารสูงสุด หรือข้อมูลยังไม่ครบ) |

### D.7 การ resolve ผู้อนุมัติแบบ "ตำแหน่งสัมพัทธ์" — สูตร

```
relative: chief
  → employee = GET /employees/{ผู้ยื่น}
  → ถ้า employee.chief == null           → บล็อก: "ไม่พบหัวหน้าโดยตรงของคุณในระบบ ติดต่อฝ่ายไอที"
  → ผู้อนุมัติ = employee.chief.emp_id
  → ถ้า GET /employees/{chief}.is_active == false → บล็อก: "หัวหน้าของคุณไม่ได้อยู่ในระบบแล้ว ติดต่อฝ่ายไอที"

relative: department_head
  → employee = GET /employees/{ผู้ยื่น}
  → ถ้า employee.department == null      → บล็อก: "คุณยังไม่ได้สังกัดแผนกในระบบ ติดต่อฝ่ายไอที"
  → dept = GET /departments  แล้วหา id == employee.department.id
  → ถ้า dept.head == null                → บล็อก: "แผนก {name} ยังไม่ได้ตั้งหัวหน้าแผนก ติดต่อฝ่ายไอที"
  → ผู้อนุมัติ = dept.head.emp_id
```

- ทำ resolve **ตอนกดส่ง** (ไม่ใช่ตอนสร้างร่าง) และเก็บผลลง snapshot ของคำร้อง
- ทุกกรณี "บล็อก" ต้องเกิด**ก่อน**ออกเลขที่เอกสาร — ไม่ให้เปลืองเลข
- ผู้ยื่นเป็น chief ของตัวเองไม่ได้ในทางข้อมูล แต่ `department_head` อาจเป็นตัวผู้ยื่นเอง (ผู้จัดการยื่นใบ) — ระบบยอมให้ (ข้อ 7.5)

### D.8 sync `users` รายวัน — ลำดับที่แนะนำ

```
1. GET /departments                     → เก็บ map id → {name, head}
2. GET /employees?active=all            → ทุกคน
3. สำหรับแต่ละคน: upsert users โดย $set เฉพาะฟิลด์จาก API + syncedAt
   (ห้ามแตะ roles, lastLoginAt, และฟิลด์อื่นที่ระบบคุณเป็นเจ้าของ)
4. คนที่อยู่ใน users แต่ไม่อยู่ใน API แล้ว → ตั้ง is_active=false (อย่าลบ — คำร้องเก่าอ้างถึง)
5. บันทึกเวลา sync ล่าสุด + จำนวน ลง settings เพื่อแสดงหน้า admin
```

- รันตอน start ระบบ 1 ครั้ง + ทุกวัน 06:00 + ปุ่มกดเองในหน้า admin
- ล้มเหลว → log + แสดงในหน้า admin ว่า sync ล่าสุดล้มเหลวเมื่อไหร่ · ไม่ crash

### D.9 ตัวอย่าง client (JavaScript — ให้ AI แปลง)

```js
const BASE = process.env.SELLCENTER_URL;
const TOKEN = process.env.ORG_API_TOKEN;
const MOCK = process.env.ORG_API_MOCK === '1';

async function orgGet(path) {
  if (MOCK) return readMock(path);                       // อ่าน mock/org/*.json ตามภาคผนวก A
  const res = await fetch(new URL(path, BASE), {
    headers: { 'x-service-token': TOKEN },
    signal: AbortSignal.timeout(5000),
  });
  const body = await res.json().catch(() => ({}));
  if (res.status === 404) return null;
  if (!res.ok || !body.success) throw new Error(`org api ${res.status}: ${body.error || 'unknown'}`);
  return body.data;
}

const orgApi = {
  employees: (opts = {}) => orgGet('/api/org/employees?' + new URLSearchParams(opts)),
  employee:  (empId)     => orgGet('/api/org/employees/' + encodeURIComponent(empId)),
  departments: ()        => orgGet('/api/org/departments'),
};
```

### D.10 เช็คลิสต์ตอนได้ token จริง (ทำวันอังคาร)

- [ ] `curl -H "x-service-token: $ORG_API_TOKEN" $SELLCENTER_URL/api/org/departments` → `success: true` และทุกแผนกมี `head` ไม่เป็น null (ถ้ามี null แจ้งไอทีตั้งให้)
- [ ] `/api/org/employees` → บัญชีทดสอบ 3–4 คนอยู่ครบ มี `chief` ครบ
- [ ] `/api/org/employees/{emp_id ของคุณ}` → `id` ตรงกับ `sub` ที่ได้จาก `/system81/userinfo`
- [ ] ส่ง token ผิด → 403 · ไม่ส่ง → 401
- [ ] สลับ `ORG_API_MOCK=0` แล้วระบบทำงานเหมือนตอน mock ทุกอย่าง โดยไม่แก้โค้ด

ตรวจว่าเป็น standalone จริง (ควรได้ error ว่า not running with --replSet):
```js
rs.status()
```

ใส่ใน `.env` บน server (ไอทีทำ ไม่ส่งให้นักพัฒนา):
```
MONGODB_URI=mongodb://itsFormsOwner:<pwd>@digital.in.th:27017/its_forms?authSource=its_forms
```

- **ไม่ต้องสร้าง collection หรือ index ล่วงหน้า** — แอปสร้างเองตอน start (E.3)
- user นี้ไม่มีสิทธิ์ `dbAdmin` ของฐานอื่น และไม่มี `clusterAdmin` — ถ้าแอปพยายามทำอะไรนอก `its_forms` จะถูกปฏิเสธ (ตั้งใจ)
- ถ้าจะให้นักพัฒนา**ทดสอบกับ server จริงจากบ้าน** (ไม่แนะนำ) ให้สร้าง db แยก `its_forms_dev` + user แยก อย่าใช้ตัวเดียวกับ production

### E.2 ฝั่งนักพัฒนา — compose สำหรับ dev (copy ไปใช้ได้เลย)

`docker-compose.yml`:
```yaml
services:
  mongo:
    image: mongo:5.0                 # ⭐ ต้อง 5.0 เท่านั้น ห้ามเปลี่ยนเป็น latest / 6 / 7
    command: ["mongod", "--bind_ip_all"]   # ⭐ ไม่มี --replSet = standalone เหมือน production
    ports:
      - "27017:27017"                # เผื่อเปิดด้วย MongoDB Compass จากเครื่อง
    volumes:
      - mongo-data:/data/db
    healthcheck:
      test: ["CMD", "mongo", "--quiet", "--eval", "db.runCommand('ping').ok"]
      interval: 10s
      timeout: 5s
      retries: 5

  app:
    build: .
    env_file: .env
    ports:
      - "${PORT:-3000}:${PORT:-3000}"
    volumes:
      - uploads:/data/uploads
      - .:/app                       # dev เท่านั้น — hot reload; ตัดออกใน production
    depends_on:
      mongo:
        condition: service_healthy

volumes:
  mongo-data:
  uploads:
```

`.env` สำหรับ dev:
```
MONGODB_URI=mongodb://mongo:27017/its_forms     # ไม่มี user/pass ใน dev ก็ได้ (container network เท่านั้น)
UPLOAD_DIR=/data/uploads
```

`docker-compose.prod.yml` (ไอทีใช้ตอน deploy — ไม่มี service `mongo`):
```yaml
services:

    build: .

    ports:
```

ตรวจว่าตั้งถูก:
```bash

docker compose exec mongo mongo --quiet --eval "db.version()"        # ต้องขึ้น 5.0.x
docker compose exec mongo mongo --quiet --eval "rs.status()"          # ต้อง error: not running with --replSet
```

- บน Mac Apple Silicon `mongo:5.0` มี image arm64 ใช้ได้ปกติ · บน Windows ใช้ Docker Desktop + WSL2
- ล้างข้อมูล dev ทั้งหมด: `docker compose down -v` (ลบ volume) — ใช้บ่อย ๆ ตอนทดสอบ ไม่ต้องกลัว
- **ห้าม**: MongoDB Atlas, `--replSet`, image เวอร์ชันอื่น, Mongo ที่ติดตั้งบนเครื่องตรง ๆ (เวอร์ชันจะไม่ตรง)

### E.3 สิ่งที่แอปต้องทำเองตอน start (idempotent — รันซ้ำได้ไม่พัง)

```js
// เรียกทุกครั้งที่ start ก่อนเปิดรับ request — createIndex ซ้ำไม่ error ถ้า spec เหมือนเดิม
await db.collection('submissions').createIndex({ docNumber: 1 }, { unique: true, sparse: true });
await db.collection('submissions').createIndex({ status: 1, 'current.approverEmpIds': 1 });
await db.collection('submissions').createIndex({ 'submitter.emp_id': 1, createdAt: -1 });
await db.collection('submissions').createIndex({ formId: 1, submittedAt: -1 });
await db.collection('users').createIndex({ emp_id: 1 }, { unique: true });
await db.collection('files').createIndex({ submissionId: 1 });
await db.collection('files').createIndex({ uploadedAt: 1 });            // job กวาดไฟล์กำพร้า
await db.collection('notifications').createIndex({ status: 1, createdAt: 1 });
await db.collection('audit_logs').createIndex({ at: -1 });
```

- ถ้า `createIndex` ล้มเหลว (เช่น ข้อมูลเก่าซ้ำ) ให้ **start ไม่ขึ้นพร้อมข้อความชัด** — ดีกว่ารันต่อแบบไม่มี index แล้วช้าโดยไม่รู้
- ไม่ต้องมีระบบ migration ใน v1 — โครงเอกสารเปลี่ยนได้เพราะ Mongo ไม่บังคับ schema แต่ **ห้ามเปลี่ยนความหมายของฟิลด์ที่มีข้อมูลแล้ว** (เพิ่มฟิลด์ใหม่ได้ เปลี่ยนชนิดฟิลด์เดิมไม่ได้) ถ้าจำเป็นให้เขียน script ปรับข้อมูลแยกและคุยก่อน

### E.4 ทดสอบว่าโค้ดไม่แอบพึ่ง transaction

เพิ่ม test หรือ script ที่รันกับ Mongo ใน compose (standalone) แล้วเดินครบข้อ 8.10 — ถ้าโค้ดเผลอเรียก `startSession().withTransaction` จะได้ error `Transaction numbers are only allowed on a replica set member or mongos` ทันที · ทำเป็นส่วนหนึ่งของ `npm test` เพื่อกัน AI แอบใส่ transaction เข้ามาทีหลัง
